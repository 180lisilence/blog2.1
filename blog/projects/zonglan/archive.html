壹

破解算法

存档格式 .boh 本质是 SQLite 数据库，正文藏在 userdata 表非 .meta 行的最长 buffer 中，经过"组内倒序 + 循环移位 + GBK 编码"三重加工。

解码（读取）

  • blob → 每 16 字节组内倒序
  • 逐字节 ROL3：((b<<3)|(b>>5))&0xFF
  • GBK 解码（errors=replace 容错）
  • 尾部 raw.rfind(',"CID":') 截断，补 ',"CID":9}]}}'

编码（保存）

  • JSON 紧凑序列化
  • GBK 编码（逐字节容错）
  • ROR3 循环移位
  • 每 16 字节组内倒序 → blob

关键约束

解码/编码步骤顺序不能颠倒；保存必须 VACUUM（否则文件翻倍）；必须更新内部 path（否则游戏识别不到）；CID=9 是固定填充值（普通玩家存档适配）；存档大部分 GBK，但功能名/谋士名/UI 文本是 UTF-8 字节混存。

游戏识别存档四要素（必须全一致）

  • 文件名 {uuid}.boh
  • 主数据行 path=/{uuid}
  • meta 行 path=/{uuid}.meta
  • index.json 纯字符串数组注册

存档结构

  • 顶层 data['Serialization']：tbVersionInfo（tbVersionPostfix + tbVersion:[9,2,1]）+ tbObjInfos（3442 个对象，每个 {CID, tbData}）
  • CID=64 对象（49 个，只有第一个含 tbBoomData 是主存档）：m_tbSource 资源数组（索引 0=ID1 金钱…索引 24=ID25 精华）、m_nPassedDays 已过天数、prosperity 繁荣度得分、prosperityLevel 繁荣等级、boomLevel 鸿业品阶、tbBankData 银行数据
  • CID=11 对象（1 个）：时间信息（m_nYear / m_nDay / m_nSeason / m_nHour）

一键解析存档工具（save_parser）

  • 位置：D:\pingye_pack\save_parser\（一键解析存档.bat 双击启动、save_parser.py 核心脚本、README.txt）
  • 功能：解码 .boh 存档文件，显示关键信息（天数、品阶、繁荣度、资源、人口等），导出完整 JSON（同目录 <文件名>_decoded.json）
  • 解码流程：.boh=SQLite → userdata 表最长 buffer → 16 字节倒序 → ROL3 → GBK → JSON
  • 关键信息提取：CID=64 对象（tbBaseData 资源/天数，tbBoomData 繁荣度/鸿业）+ CID=11 对象（时间）
  • 使用方法：双击 bat 选择文件/扫描目录；或拖入 .boh 文件到 bat；或命令行 save_parser.py <文件路径>
伍

存档卡 3/4 修复（TRANSLATE_V）

  • 现象：新建存档后加载卡 3/4（"存档打不开"）
  • 根因：新建存档时游戏漏写 /TRANSLATE_V 标记。缺该标记的存档下次加载卡 3/4。不是创造模式的问题！原版下新建存档同样缺（证据：38700564 是原版下新建的，同样缺）
  • 判定：正常大存档主体 2112KB+ / 2171KB+；坏存档主体 670432B 且缺 /TRANSLATE_V

修复 SQL

INSERT OR IGNORE INTO userdata (path,size,buffer,time)
VALUES ('/TRANSLATE_V',5,b'9.2.1','YYYY-MM-DD HH:MM:SS')
  • 脚本：fix_all_translate.py（补标记）、restore_all_saves.py（恢复+index+补标记）、diag_saves.py / classify_saves.py / organize_saves.py
  • 处理存档铁律：先备份 → 补 TRANSLATE_V；不要删 .boh（会触发 Steam 云同步冲突 → 启动崩溃）
  • 崩溃教训：手动删除存档 .boh → Steam 云存档同步冲突 → 游戏启动崩溃（ExceptionNotCapture30748.dat）；解法：restore_all_saves.py 一键"恢复存档 + index.json + 补 TRANSLATE_V" → 游戏恢复

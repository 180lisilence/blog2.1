贰

存档破解算法

存档格式 .boh 本质是 SQLite 数据库，正文藏在 userdata 表非 .meta 行的最长 buffer 中，经过"组内倒序 + 循环移位 + GBK 编码"三重加工。

解码（读取）

  • blob → 每 16 字节组内倒序
  • 逐字节 ROL3：((b<<3)|(b>>5))&0xFF
  • GBK 解码（errors=replace）
  • 尾部 raw.rfind(',"CID":') 截断，补 ',"CID":9}]}}'

编码（保存）

  • JSON 紧凑序列化
  • GBK 编码（逐字节容错）
  • ROR3 循环移位
  • 每 16 字节组内倒序 → blob

关键约束

解码/编码步骤顺序不能颠倒；保存必须 VACUUM（否则文件翻倍）；必须更新内部 path（否则游戏识别不到）；CID=9 是固定填充值；存档大部分 GBK，但功能名/谋士名/UI 文本是 UTF-8 字节混存。

游戏内置修改器（DLL 注入 + Lua Hook + ImGui）

  • 原理三层：DLL 注入（远程 LoadLibraryA）→ IAT Hook（lua_pcall 导入槽）→ 捕获 lua_State L → 执行 Lua 代码
  • ImGui 游戏画面内面板（窗口大小必须 ImVec2(360,430) 早期 / ImVec2(620,900) v13 大面板）
  • 线程安全：热键线程只入队，Lua 执行在主线程（my_lua_pcall 钩子）
  • 命令文件机制：写 lua_cmd.txt 下发任意 Lua 代码，DLL 每 50ms 轮询消费后删除
  • 热键 F5-F10（记录 / 恢复 / 加人口 / 加钱 / 加木 / 全资源）
  • 资源修改用 g_camp:ModifySourceValue(ID, 增量) 或直接改 g_camp.m_tbSource[ID]；人口修改必须用 API（g_camp:ModifyPopulation），不能直接改表
  • 三大修改真相：资源字符串键 bug（tonumber）、知名度双存储、繁荣度得分真相（UpdateBoom）
  • v17 路径自适应版：整个文件夹可任意移动 / 改名 / 拷贝

肆

C 方案二进制补丁 exe

直接修改游戏 exe 入口点，插入 shellcode 加载修改器 DLL，然后执行原指令跳回。最终版本 v9（IAT 寻址获取 LoadLibraryA，完全不受 ASLR 影响）。

  • 关键技术突破：ASLR 相对跳转（E8/E9）、代码洞穴映射（修改 .text virtual_size 0x60BE8E→0x60C000）、IAT 寻址 LoadLibraryA（IAT 条目 RVA=0x0060D258）、延迟初始化（Sleep3 秒→检测 Lua5X64.dll→Sleep2 秒→Hook）
  • PE 结构关键参数：入口点 RVA=0x0049D28C、代码洞穴 RVA=0x0060CE90（368 字节）、ImageBase=0x140000000
  • A+C 合并版：trainer_v15_delayed.dll（延迟初始化 + 自动加载面板与监控）
  • 测试结果：游戏正常启动，运行 15 秒+ 无崩溃，DLL 成功加载，热键线程启动
伍

pakv4 解包与重打包（ZSTD）

000.dat 无加密，纯 ZSTD 压缩（标准 ZSTD 魔数 0x28B52FFD 小端），重打包 100% 可行。

  • 重打包流程：解析 Trunk.dir → 提取 ZSTD 块 → 解压 → 修改 → 重新压缩（级别 15+）→ 写回（覆盖或追加 + 更新目录条目）
  • 压缩级别测试：级别 15+ 压缩后大小 <= 原大小，可以直接覆盖（级别 22 最佳 6.60:1）
  • 盲解包统计（前 100MB）：3997 个 ZSTD 块（99.97% 成功）、1052 个 Lua 文件、557 个 JSON 文件、2387 个未知类型
  • 已验证推翻：❌"Lua 脚本加密存储"→ 实际 ZSTD 压缩；❌"重打包不可行"→ 实际完全可行
陆

Steam 唤醒启动

问题

直接启动游戏 exe（任何方式，包括 subprocess / Popen / Task Scheduler）都会导致游戏崩溃或退出。

根因

游戏存档路径 = FS.GetCwd()/storage/<userFolder>（archive_mgr.lua L206）。工作目录必须为游戏根目录，存档系统才能找到 storage/offlineuser；直接以 bin64 或其他工作目录启动 → 无存档上下文 → 进游戏场景时 CreateScene 崩溃。

解决方案

用 steam://rungameid/<appid> 协议唤醒 Steam 启动游戏；Steam 以游戏根目录为工作目录拉起游戏，存档路径正确；启动前自动做 Steam 云同步（可恢复被删除的存档）；散文件/模拟器模式在 Steam 启动下行为与手动从 Steam 库启动完全一致。所有模式（原版/创造/离线）统一走此路径。

存档卡 3/4 修复（TRANSLATE_V）

  • 现象：新建存档后加载卡 3/4（"存档打不开"）
  • 根因：新建存档时游戏漏写 /TRANSLATE_V 标记。缺该标记的存档下次加载卡 3/4。不是创造模式的问题！原版下新建存档同样缺
  • 判定：正常大存档主体 2112KB+ / 2171KB+；坏存档主体 670432B 且缺 /TRANSLATE_V

修复 SQL

INSERT OR IGNORE INTO userdata (path,size,buffer,time)
VALUES ('/TRANSLATE_V',5,b'9.2.1','YYYY-MM-DD HH:MM:SS')
  • 脚本：fix_all_translate.py（补标记）、restore_all_saves.py（恢复+index+补标记）、diag_saves.py / classify_saves.py / organize_saves.py
  • 处理存档铁律：先备份 → 补 TRANSLATE_V；不要删 .boh（会触发 Steam 云同步冲突 → 启动崩溃）

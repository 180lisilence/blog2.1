版本 2.0 — 存档破解 + 多方案探索

存档破解（已完成）

  • 存档格式：.boh = SQLite 数据库，正文在 userdata 表非 .meta 行的最长 buffer
  • 解码算法：blob → 每 16 字节组内倒序 → 逐字节 ROL3 ((b<<3)|(b>>5))&0xFF → GBK errors=replace → 尾部 raw.rfind(',"CID":') 截断，补 ',"CID":9}]}}'
  • 编码算法（保存）：JSON 紧凑序列化 → GBK → ROR3 → 每 16 字节组内倒序 → blob

关键约束

  • 解码 / 编码步骤顺序不能颠倒
  • 保存必须 VACUUM（否则文件翻倍）
  • 必须更新内部 path（否则游戏识别不到）
  • CID=9 是固定填充值（普通玩家存档适配）
  • 存档大部分 GBK，但功能名 / 谋士名 / UI 文本是 UTF-8 字节混存

游戏识别存档四要素（必须全一致）

  • 文件名 {uuid}.boh
  • 主数据行 path=/{uuid}
  • meta 行 path=/{uuid}.meta
  • index.json 纯字符串数组注册

存档结构

  • 顶层 data['Serialization']：tbVersionInfo（tbVersion:[9,2,1]）+ tbObjInfos（3442 个对象，每个 {CID, tbData}）
  • CID=64 对象（49 个，只有第一个含 tbBoomData 是主存档）：tbBaseData.m_tbSource 资源数组 / m_nPassedDays 已过天数 / tbBoomData.prosperity 繁荣度 / prosperityLevel 繁荣等级 / boomLevel 鸿业品阶 / tbBankData 银行数据
  • CID=11 对象（1 个）：时间信息（m_nYear / m_nDay / m_nSeason / m_nHour）

64 个 CID 完整字典（存档层）

CID 与资源 ID 是两套完全独立编号：CID = 存档对象类型编号（如 CID=19 是建筑记录）；资源 ID = m_tbSource 槽位号（如 ID19=盐）。

C 方案：二进制补丁 exe（project3，最终成功，v9 IAT 寻址）

目标：直接修改游戏 exe 入口点，插入 shellcode 加载修改器 DLL，然后执行原指令跳回。

  • 最终版本：v9（IAT 寻址获取 LoadLibraryA，完全不受 ASLR 影响）
  • 测试结果：游戏正常启动，运行 15 秒+ 无崩溃，DLL 成功加载，延迟初始化正常，IAT Hook 成功，热键线程启动

关键技术突破（按解决顺序）

  • ASLR 问题：游戏启用 DYNAMIC_BASE，shellcode 不能用绝对地址 → 用相对跳转（E8/E9）
  • 代码洞穴映射问题：代码洞穴在 .text 节区 virtual_size 之外不被映射 → 修改 virtual_size 从 0x60BE8E 改为 0x60C000
  • LoadLibraryA 地址获取：不能硬编码（ASLR）、PEB 遍历太复杂 → 通过游戏导入表（IAT）条目获取，IAT 条目 RVA=0x0060D258
  • DLL 加载时机：DLL 在游戏入口点加载时核心子系统未初始化 → 延迟初始化（Sleep3 秒 → 检测 Lua5X64.dll → Sleep2 秒 → Hook）

PE 结构关键参数

  • 入口点 RVA=0x0049D28C，文件偏移=0x0049C68C，ImageBase=0x140000000
  • 代码洞穴 RVA=0x0060CE90，文件偏移=0x0060C290，大小 368 字节
  • 原入口点指令：48 83 EC 28（sub rsp,0x28）+ E8 DF 08 00 00（call）
  • 原 call 目标 VA=0x000000014049DB74，跳回地址 VA=0x000000014049D295（入口点+9）
  • LoadLibraryA IAT 条目 RVA=0x0060D258；.text 节区 VSize=0x60BE8E（原）→ 0x60C000（修改后）

pakv4 解包与重打包（ZSTD 无加密，重打包可行）

  • 解包工具：PakV4Extract.exe（C++，MinGW 静态编译，基于 GitHub jx3pak）

  • 递归解包：从 camp_boom.lua 开始，搜索 ImportScript 引用，5 轮后共解包 172 个 Lua 文件（GBK 编码）
  • pakv4 格式：Trunk.dir（魔数"DIRFILE"）+ 数字分区目录（0,1,2,3,4,998,999,1000-1018）
  • 压缩算法确认是 ZSTD（标准 ZSTD 魔数 0x28B52FFD 小端）

重大突破（2026-09-03 晚）：000.dat 无加密，纯 ZSTD 压缩！重打包 100% 可行

之前"搜索不到明文 Lua"是错误结论：在压缩数据里搜明文当然搜不到，这是正常现象，不是加密。验证：000.dat.bak（381MB）前 50MB 找到 3637 个 ZSTD 块，前 20 个块 20/20 全部解压成功；解压后是明文 Lua 脚本与 JSON 配置文件。ZSTD 解压工具：Python zstandard 库（pip install zstandard）。

重打包方案（已验证可行）

  1. 解析 Trunk.dir 目录条目，获取每个文件的 offset、compressed_size、decompressed_size
  2. 从 000.dat 提取对应 ZSTD 块，解压得到明文文件
  3. 修改目标文件（如 camp_boom.lua）
  4. 用 ZSTD 重新压缩（压缩级别 10+，确保压缩后大小 <= 原大小）
  5. 写回 000.dat：新压缩大小 <= 原大小 → 直接覆盖原 offset 处，剩余空间用 0x00 填充；否则追加到末尾并更新目录条目 offset
  6. 更新 Trunk.dir 目录条目：decompressed_size（如果文件大小变了）

重打包完整验证（camp_boom_2.lua，繁荣度模块 LCampBoom 类）

  • 偏移 0x000BD327；原压缩大小 16128 字节；原解压大小 100241 字节（GBK 明文）；压缩比 6.22:1；原版压缩级别约 10 级

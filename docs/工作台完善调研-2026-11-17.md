## 一、现状盘点

### 1.1 技术架构

- **纯静态 SPA**：`index.html` 加载 `boot.js / store.js / ui.js / api-ai.js` 和 11 个模块脚本，hash 路由（`#/home`、`#/todayPlan`…），无构建、无框架、无懒加载。
- **数据流**：模块 → `Store.DBadd/DBput/DBdelete` → 内存 `appStore` → 300ms 防抖 → `BS.set` → `PATCH /api/data/all` → MySQL `user_data`。
- **启动流程**：`blog-storage.js` 先读 `localStorage` 快照（`bs2_cache`）预热，再异步 `GET /api/data/all` 拉服务端全量覆盖；5 秒兜底防止一直“加载中”。
- **鉴权与安全**：`/blog/workbench` 走 authGate 登录保护；数据接口要 web session；写操作带 CSRF 双提交。AI 请求走 `POST /api/ai/chat` 服务端代理，Key 不落库、不落日志。
- **响应式**：`styles.css` 5 个断点（900px×2、768px、640px、769px+），900px 以下侧栏变抽屉并支持手势；另有 `workbench-enhance.css` 做主题/细节覆盖。
- **数据配额**：服务端 `DATA_MAX_TOTAL_BYTES = 2MB`、`DATA_MAX_KEYS = 500`，请求体上限 1MB（`server.js:78`）。

### 1.3 数据现状（服务器实测，只读聚合）

- `user_data` 共 **5 行**，总 **171.8KB**，单条最大 **174,415 字节**（约 170KB，就是一份完整 workbench 快照）。
- 有 workbench 数据的账号 3 个，另有 2 个 `personal_profile`。
- 结论：离 2MB 配额还很远，但 **AI 消息只增不减**，长期会先撞 1MB 请求体上限。

### 1.4 已经具备、不需要重复造的能力

- 回收站：删除入 `recycleBin`，支持恢复、彻底删除、清空。
- 设置页：JSON 导出（`workbench-backup-YYYY-MM-DD.json`）、导入恢复、一键重置。
- 到期提醒：`boot.js` 里有 Notification 检查（需用户授权、只在页面打开时跑）。
- 侧栏折叠、移动抽屉 + 手势、深浅主题、头像压缩上传、AI 多会话与模型扫描。

## 二、问题清单（按优先级）

### P0 · 数据可靠性

1. **保存失败没有可靠的重试入口**
   `blog-storage.js` 的 `push()` 失败后会把改动放回 `dirty` 队列并保本地快照，但只靠下一次改动再触发推送；用户如果失败后直接关页，`beforeunload` 里的 `push()` 是 fire-and-forget，**最后一次修改可能丢**。界面上只有“⚠️ 云端保存异常”，没有“重试/查看待同步”按钮。

2. **多端并发是 last-write-wins，静默覆盖**
   `PATCH /api/data/all` 以 **store 数组为粒度**整包合并。两端同时改同一模块（比如手机加待办、电脑删待办），后写的一端会把先写的数组整体覆盖，没有版本号、没有冲突提示。当前没有 `updatedAt` 级别的合并策略。

3. **没有 schemaVersion，导入不校验结构**
   `migrateConfig` 只处理 `config.global` 这类配置；各 store 的条目结构没有版本字段。设置页导入只判断“是不是 object”（`setting.js:412`），**任意 JSON 都能灌进来**，字段缺失/类型错会在渲染时炸或静默丢。

4. **AI 对话无上限增长**
   `aiMsgs` 全量存进 workbench 一个大 JSON，只有删除会话时才 `DBpurge`；发请求时只 `slice(-20)` 取上下文（`aiPage.js:194`），但**存储层不截断**。长期使用会逼近 1MB 请求体 / 2MB 配额，届时整个 workbench 保存都会失败。

### P1 · 体验与产品

5. **没有全局搜索 / 命令面板**
   11 个模块、数据分散在 12 个 store，找一条待办或一个项目只能逐页翻。目前没有任何跨模块检索入口。

6. **没有日历 / 周视图**
   `todayPlan` 是平铺列表，`deadline` 只在首页做 24h 聚合；看不到一周节奏，也无法拖拽排期。

7. **提醒依赖“页面开着”**
   到期检查在 `boot.js:214` 启动时跑一次；关掉页面就收不到。没有服务端定时推送、没有邮件/微信通道。

8. **移动端 11 项导航仍偏长**
   抽屉 + 手势已可用，但模块多、层级平；缺少底部 Tab、最近使用、常用模块置顶。

9. **缺少跨模块关联与批量操作**
   项目 ↔ 任务 ↔ 文章/发布计划之间没有引用字段；没有多选、批量完成/删除、拖拽排序、标签体系。

10. **状态反馈粗糙**
   空态、加载态、错误态基本是清空 + toast；没有骨架屏、没有失败重试、没有“离线/待同步”明确状态。状态条初始文案在未验证前就显示“云端已连接”，断网时误导。

11. **可访问性不足**
    大量 `div` 当按钮、缺 `aria-label`/`role`、键盘 Tab 顺序与 ESC 关闭不完整，移动端点击区域偏小。

12. **疑似小 bug：首页高优摘要 store 名可能显示 `?`**
    `home.js:94` 用 `i._store || '?'`；`DBadd` 会写 `_store`，但 `DBput` 不补。历史数据或导入数据缺这个字段时，摘要会显示 `?`。属于显示瑕疵，需用真实数据复现确认。

### P2 · 技术债

13. `index.html` 仍有内联主题脚本和内联 `.back-to-blog` 样式。当前 CSP 允许 `unsafe-inline`，能跑；但一旦收紧 CSP 就会断，属于未来迁移项。
14. `styles.css` 41.8KB + `workbench-enhance.css` 8KB 覆盖层，组件样式没有分层，后续改主题/换肤成本高。
15. `innerHTML` 注入面仍在：`profile.js` 头像拼 `<img src="...">`、`boot.js` 错误面板。值虽来自用户自己的 data URL，仍建议改成 DOM 构建 + 协议白名单。
16. 11 个模块脚本首屏全量同步加载；当前体积小无所谓，模块变多后需要按需加载与缓存指纹统一。
17. **没有自动化测试**：store 迁移、同步、回收站、权限这些高风险逻辑全靠手测。

## 三、方案调研（外部借鉴 + 本项目适配）

| 借鉴对象 | 做法 | 适配到工作台 |
|---|---|---|
| VS Code / Linear | `Ctrl+K` 命令面板，键盘优先 | 全局搜待办/项目/笔记/文章，回车直达；成本最低、收益最高 |
| Sunsama / Akiflow | 今日时间轴 + 逾期泳道 | 把 `todayPlan` 升级成“今天时间块 + 逾期区”，不改存储结构先做视图 |
| Todoist | 自然语言录入（“明天 3 点 交周报 #开发”） | 快速录入框解析日期/优先级/模块，落到对应 store |
| Obsidian | 本地优先 + 离线队列 | 现有 `BS` 已是“服务端权威 + 本地快照”，补一个可见的待同步队列即可 |
| Notion Calendar / PWA | 可安装、离线打开、后台提醒 | 二期做 manifest + Service Worker；提醒需要服务端定时任务才有意义 |

**技术选型结论**：不引入 React/Vue，不换构建链。保持原生 JS + 现有 REST 数据层，先把“聚合、检索、提醒、可靠性”做好。理由是工作台只有 5k 行、单用户为主，引入框架的收益低于迁移成本。

## 四、推荐路线图

### 阶段 0 · 稳定性（预计 1–2 天）
- 保存状态机：`saving / saved / failed / pending` 四态，失败给“重试”按钮和待同步条数。
- 修 `_store` 缺失：`DBput` 统一补 `_store`，老数据一次性回填。
- AI 消息上限：每会话保留最近 N 条（如 200 条）或总字节阈值，超出归档/截断。
- `schemaVersion` + 导入校验：按 store 定义字段白名单/类型，非法导入直接拒绝并提示。
- 并发提示：保存前比对服务端 `updated_at`，落后时提示“另一端已更新”。

**验收**：断网改 3 条 → 恢复网络 10 秒内自动补传；刷新后一致；失败可见可重试。两端同时改同一模块有冲突提示，不静默丢数据。

### 阶段 1 · 聚合与检索（预计约 1 周）
- 全局搜索 / 命令面板（`Ctrl+K`，移动端搜索入口）。
- 首页重构为“今日聚焦”：到期、高优、习惯、快速录入四块，减少跳转。
- 日历/周视图（先只读展示，再支持拖拽改期）。
- 提醒中心：页面内红点 + 浏览器通知 + 逾期汇总；后续再接服务端定时任务。
- 移动端底部 Tab（首页/计划/搜索/我的），侧栏保留完整模块。

**验收**：375×667 下无横向滚动，一键切模块；搜索能在 1 次输入内命中跨模块条目。

### 阶段 2 · 平台化（预计 1–2 周）
- 标签 / 关联（项目 ↔ 任务 ↔ 发布计划）、批量操作、拖拽排序。
- PWA：manifest + Service Worker，可安装、离线打开。
- 按条目 `updatedAt` 做冲突合并，替代整包覆盖。
- 模板与复盘：周报模板、习惯 streak、模块使用统计。

### 阶段 3 · UI 美化（最后）
- 统一设计 token（颜色/间距/圆角/阴影）、CSS 分层、深浅色对比度校验、动效与骨架屏。
- 现在骨架没稳，不建议先调样式。

## 七、第一批修复记录（2026-11-17 晚）

已落地并上传服务器验证：

1. **修复新设备空数据覆盖云端**：`initStore` 现在先等 `BS.ready`（云端首次全量拉取结束）再读数据；只有确认连上云端且账号确实为空时才初始化写盘，离线/未登录只写本地。
2. **保存失败可见、可重试**：`BS` 增加 `saving / saved / failed / local` 状态回调与指数退避自动重试（1.5s→30s 封顶）；状态条显示「待同步 N 项 · 点此重试」，点击即可手动重试。
3. **修复 `Store.appStore` 是旧引用**：改为 getter，始终指向 initStore 后的真实数据；设置页导出/导入不再操作最初那个空对象。
4. **修复保存期间丢改动**：`isSaving` 时不再直接 return，改为排队再存一次。
5. **补齐 `_store`**：`DBput` 统一写入 `_store`；`migrateSchema` 给历史条目回填；首页高优摘要改为按来源数组直接标注模块名，并在点击时跳到对应模块。
6. **AI 消息上限**：单会话保留最近 200 条、全局最多 2000 条，超出自动丢弃最老的，避免顶到 1MB 请求体 / 2MB 配额。
7. **导入校验**：新增 `validateImport`，按 store 校验数组与条目结构；导入改为真正的「覆盖」语义（先清空再写入），非法 JSON 直接拒绝。
8. **数据版本**：新增 `_meta.schemaVersion`（当前 2），加载时自动迁移。

仍待下一批：

- 多端并发冲突检测（需要服务端返回 `updated_at` 并做 409 比对）。
- 真机视觉走查与 2MB 边界压测。
